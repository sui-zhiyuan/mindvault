# 负载因子扫描（n 固定，容量变化）

n=32,768，`--reserve --capacity C`，查询全部 key；std hasher；10 reps 中位数。

负载 = n / C；容量越小，表越小、探测越长。

| 负载 | 容量 C | ARM cyc/q | x86 cyc/q（估） | 比值 |
|---:|---:|---:|---:|---:|
| 0.30 | 109,227 | 58.6 | 49.0 | 1.19 |
| 0.50 | 65,536 | 56.9 | 46.1 | 1.24 |
| 0.70 | 46,812 | 46.4 | 39.9 | 1.16 |
| 0.85 | 38,551 | 46.4 | 40.9 | 1.13 |
| 0.95 | 34,493 | 46.2 | 40.4 | 1.14 |

## 观察

- 从负载 0.70 到 0.95，每查询周期几乎不变（46.4→46.2 / 39.9→40.4）：**探测长度不是主因**。
- 负载 0.30/0.50（表更大：~3.5 MiB / ~2 MiB）两机都变慢，ARM 比值升到 1.19–1.24：**差距随表footprint增大而上升**。
- 这与 n 扫描的结论一致：固定开销 ~1.1–1.3×，表超过缓存后叠加访存成本。

## 局限

- `--capacity` 是条目容量，实际桶数由 hashbrown 取整，真实负载因子与标称有偏差；
- 只测了 std，未测 identity/mix；
- x86 周期仍为「墙钟 × 4.45 GHz」估算。

原始数据：`arm_ld*.json`、`x86_ld*.json`。
