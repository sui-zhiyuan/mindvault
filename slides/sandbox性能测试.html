21500 规模：并发 c 扫描——超过 100 即崩溃

滚动窗口，verify=off 方法论（POST 2xx + Cubelet 日志对账）。c=100 是 Cubelet create 工作流硬限流的设计值：resume 超限被秒拒，create 超限在上游排队挤爆 30s 路由超时，pause 无流控但资源侧劣化撞 120s。

成功率随 c 的崩溃曲线

c=100 → 300 → 600（pause/resume 作用于上一波幸存沙箱）

pause@c=300 虽 100% 成功但 p95 115.8s 已贴住 120s 路由超时；resume@c=600 的 82.1% 基于 n=112（pause@c600 崩溃后仅 112 个可恢复），且 12 个失败为流控秒拒。

create 的五条路（1500 全量拉起）

30s 产品路由契约内 vs 放宽超时后的单波

契约内最优 = c=100 滚动（90.5%）；追求全量最快 = c=1500 单波 + 路由超时放宽到 300s：62.2 s 完成 99.93%（1499/1500）。两者不可兼得。

为什么三个操作的最优值都收敛到 c=100？　部署配置 /usr/local/services/cubetoolbox/Cubelet/config/config.toml 中 flows.create.concurrent = 100（工作流引擎 TryAcquire 非阻塞，超限立即报 130513 flow [create] exceed limited）。 create 与 resume 共用该流程：resume 在飞 >100 → 立即 500 秒拒（c=300 实测 805/912 秒拒）；create 在飞 >100 → 上游排队直至 30s 408（c=600 实测 901×408）。 pause 不走流控，劣化纯资源侧（数百并发快照写争用）。c=100 不是经验折中，而是贴合系统的设计并发天花板。

3100 规模：最优 c 的权衡（墙 vs 单次延迟）

pause/resume 每个 c 用全新沙箱（避免重复 pause 劣化 7-30× 污染数据）；含状态确认的整波墙。

整波墙（越短越好）

n=100，统一起跑后到全部完成

create c=100 为 4 轮区间（0.40-1.39s 抖动，取 0.40）；resume c=50 的 8.40s 是 1 例 ResetVm 3s 悬崖失败重试拖长的异常值，其延迟分布仍有效。create 在 c=25 后墙不再缩短。

单次请求延迟 p95（越低越好）

纯服务端 RTT，不含排队起表

c 由 25 → 100：create p95 94.8→~419 ms、pause 429→787 ms、resume 140→1091 ms——加并发只抬高单次延迟，不再缩短整波。故 100 规模推荐 create 25 / pause 25 / resume 10。

4机制：占用爬坡与负载镜像（1500 规模 c=100 波内）

create 延迟不是并发数的函数，而是已运行 VM 数（占用）的函数——波次自己制造超卖环境：2706 vCPU 挤 384 物理核（~8:1），loadavg 爬到 ~2100。

create 波内 RTT 爬坡（11× 劣化）

按起跑顺序四分位：Q1 占用≈0 → Q4 占用≈1300+

晚到的 create 被"既有租户"饿到接近 30s 路由超时——这正是 1500 规模失败集中的地方（失败为占用驱动，降 c 不能避免）。

负载镜像：pause 越做越快，resume 越做越慢

波首 vs 波尾的平均 RTT（ms）

pause 波内 VM 陆续暂停释放 CPU（loadavg 2100→280），RTT 递减；resume 波内 VM 陆续恢复、负载爬回，RTT 递增（波尾取 Q3 值）。大规模滚动操作存在"先来先服务"的公平性效应。

pause 路径既无 ResetVm 对时也无流控（停 vCPU + 写快照不需要 guest 配合），故 1357/1357 全部成功。

根因与修复证据（C5）

shim→guest 对时 RPC 硬超时 3s（CubeShim sb.rs:107）
超卖宿主机上刚拉起的 guest 3s 内抢不到 CPU → RPC 超时 → 工作流失败。实测最差对时 13.7s，3s 的设置在高占用下不够用。

修复已验证：把超时 3s→30s 后复测 5 轮，ResetVm 错误 0/7500，成功率 ~93% → 99.5%；残余 0.5% 是下一层同类问题（container 模块 10s 超时）。

这是把 1500 规模 create/resume 成功率从 90-96% 提到 ~99% 的唯一大杠杆。

6C6：shim 进程泄漏——失败路径的慢性毒害与清理验证

create 失败（~30%）与 resume 失败（~80-100%）留下 CubeMaster 不感知、永不退出的 containerd-shim 孤儿，每个空转 ~2 核；pause 失败不泄漏。测试日累积 683 个 ≈ 320 核。

泄漏时间线：失败数 vs 遗留 shim

按测试波次时间窗对账（2026-09-16）

13:18 的 pause 崩溃波 484 个失败只留下 ~5 个 shim——pause 失败不泄漏的直接证据。create/resume 失败约 30%/80-100% 留下 husk。

污染 → 清理 → 基线恢复（100 规模 c=25 整波墙）

干净基线 → 683 个泄漏 shim 污染态 → SIGKILL 清理后复测

清理：SIGTERM 发出 30s 后 683 个全部存活（husk 不响应常规终止信号），pkill -9 后清零，宿主机 CPU us 88.2%→4.2%。ocC100b 复测三项全部恢复基线（create p95 117.7ms vs 基线 117.4ms，逐毫秒一致）。
