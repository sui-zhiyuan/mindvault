02如何采集的

计时口径、数据源与工具链；阶段表的每一格都能回溯到原始打点。

计时口径

  • 整波 wall：bench v2 栅栏 GO → 最后一个结果返回（不含线程启动）。= 末实例 queue ＋ 末实例 RTT。
  • RTT：纯 POST 往返（单请求）。queue：GO → 拿到并发位（客户端信号量等待，非服务端延迟）。
  • 阶段边界：cube-shim-req.log 纳秒时间戳标记（每实例每波取首现），逐标记相减得段长。
  • 三个口径：p50 = 典型单请求中位；p95 = POST 尾部（= 批 1 最慢单例）；max/整波 = 末实例完成路径。

数据源（表内「口径」列标签）

[req] cube-shim-req.log 纳秒时间戳标记间隔（100 实例聚合） · [stat] Cubelet/shim stat 日志 CostTime · [perf] perf walltime（cpu-clock + sched_switch 混合双事件） · [path] stage_path.py 逐实例时间线 · [join] 三源逐实例差分（stage_upstream.py：bench RTT × req shim span × Cubelet workflow）

波窗口与对账

  • 每波前记录三日志偏移（shim-stat 行数 / Cubelet-stat 行数 / shim-req 字节偏移），波 N 的记录 = [本波偏移, 下一波偏移)，InstanceIds 过滤到本波 ids。
  • 每波 perf record -a -m 1024 -g --call-graph fp -e cpu-clock/freq={499|99|299}/ -e sched:sched_switch， perf_wall.py 按 bench 单调钟窗口裁剪，tid 配对 switch-out→in 得阻塞（S/D/R 态）。
  • 样本对账（pause 波）：cpu-clock 36,757 + sched 220,604；覆盖率 98.4%，零丢样级质量；stage_path join = 100/100（三波全对上）。

04概念性步骤分解 vs 实测阶段表：差异在哪里、为何会有

下面这张 Start·10步 / Pause·6步 / Resume·7步 是「组件功能分解」——谁参与、按什么顺序； 而 §03 的三张阶段表是「实测 walltime 分解」——哪里真正花时间、花多少。两者是不同性质的骨架，差异集中在少数几处，逐一对照如下。

Start · 10步
  • API 接入 · CubeAPI xx ms
  • 编排洗点 · CubeMaster xx ms
  • 模板镜像 · P2P 分发 xx ms
  • MicroVM 创建 · CubeHypervisor xx ms
  • Shim 集成 · CubeShim xx ms
  • KVM 创建 VM/vCPU · 内核 xx ms
  • Guest 启动 · cube-agent xx ms
Pause · 6步
  • 编排触发 · AutoPause xx ms
  • 冻结 vCPU · KVM xx ms
  • *内存快照 · CubeHypervisor xx ms
  • 设备状态保存 · virtio xx ms
  • 磁盘快照 · CubeCoW(CGO) xx ms
  • 快照落盘 · 存储 xx ms
Resume · 7步
  • 编排触发 · AutoResume xx ms

  • 设备状态恢复 · virtio xx ms

一句话差异：概念图是「功能上存在哪些步骤」，阶段表是「时间上哪些步骤有成本」。功能存在的步骤不一定花时间 （reflink 磁盘快照 ≈ 0、virtio 设备状态、vCPU 冻结 ioctl 均亚毫秒、P2P 分发不在路径）；而概念图漏掉了几处 真正花时间、却没有对应「功能步骤」的成本——51.4 ms 固定窗 sleep、Cubelet 自身冷动作、 VM 恢复启动（resume 的最大段）。这些只能用打点测出来，无法从架构图上推出来。

4.4d 为什么会差这么多：四条成因

  1. 两张图的「纵轴」不同：概念图纵轴是组件功能（谁参与），阶段表纵轴是walltime 成本（谁花时间）。功能存在 ≠ 时间有成本，所以 reflink 磁盘快照、virtio 设备状态、vCPU 冻结 ioctl 在概念图里是「一步」，在阶段表里坍缩成 ~0 或亚毫秒。
  2. a73 的存储策略把「拷贝」这类概念步骤降到了零：增量内存 dump（a00a714c）＋ XFS reflink（disks/ bytes=0），使「磁盘快照」「模板分发」「reflink 恢复」都变成本地元数据操作，概念图上看起来是成本点的地方实测几乎免费。
  3. 真正的成本藏在「看不见的等待」里，不在「动作」里：51.4 ms 固定窗（等日志转发中止的 sleep）、resume 的 VM 恢复启动（guest 恢复执行＋KVM 状态恢复，145 ms）、批 1 的 Cubelet cgroup/storage 冷动作（~100 ms）——这些没有对应的「功能步骤」，只能靠 req.log 打点 + perf D 态栈才能定位。
  4. 划分边界不同：概念图按组件边界分步（virtio 一步、KVM 一步、存储一步）；实测必须按可打点的边界分——打不到的段（virtio、vCPU ioctl）只能并入相邻窗（#3/#4/#5），因此阶段表里有「含于某窗」「无独立打点」的合并项，而概念图里它们各自成行。
结论：概念图适合描述「生命周期/组件职责」，不适合当性能账本。若用概念图指导优化，会去优化 reflink、virtio、vCPU 这些几乎免费的段； 而真正该优化的 固定窗 sleep（−38 ms/op 已实证） 和 resume 的 VM 恢复启动（145 ms） 恰恰不在概念图里。
