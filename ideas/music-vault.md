# 音乐收藏馆（Music Vault）· 需求文档

> 状态：需求澄清阶段 —— 只记需求，不做设计、不选型、不写代码
> 更新：2026-09-23
> 定位：点子/需求文档（`ideas/` 目录存放尚未进入设计与实现的构想）

## 1. 一句话意图

建一座"音乐的**索引馆**"：记录**有哪些音乐、每一首是什么、彼此之间是什么关系、在哪些平台能找到它**。

它收藏的是"关于音乐的知识"，不是音乐本身 —— 音频字节不进这座馆。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 音乐 / 曲目 | 收藏馆的最小记录单位，指一个具体的"录音版本"，不是抽象的曲谱 |
| 作品 | 词曲层面的"这首歌"，一首作品可以有多个录音版本（原唱、翻唱、现场、重制） |
| 翻唱 | 他人对已有作品的重新演唱录音 |
| 平台身份 | 同一首音乐在某个平台上的 id 与链接；一首音乐可有多个平台身份 |
| provider | 提供音乐资料/资源的来源，既包括音乐平台，也包括元数据源 |
| 离线查询 | 浏览、检索、关系遍历全部由本地库回答，不依赖网络 |

## 3. 需求原文与意图解读

| # | 原始需求 | 意图解读 |
| --- | --- | --- |
| 1 | 基础记录是音乐（包括音乐名、流派、风格等信息，并给出多个音乐平台的 id 或链接） | 以"一首音乐"为最小记录单位；每条记录是一份**可定位的身份描述**：既有内容属性（名称、流派、风格……），也有**跨平台的多个外部身份**（一首音乐 → N 个平台 id/链接，而不是只认一个平台） |
| 2 | 使用图数据库存储关系（翻唱、属于专辑、歌手等） | 关系是**一等公民**，不是附属字段。价值在于能沿关系网络走：谁翻唱了谁、某作品有哪些版本、某歌手参与过什么、某专辑收了哪些曲目 |
| 3 | 为规避版权问题，不直接保存任何格式的音乐（例如 MP3、WMV 等） | **硬约束**：收藏馆的库里不落任何音频字节 —— 不存储、不转码、不内嵌、不再分发 |
| 4 | 提供工具（导入列表、从 provider 下载等） | 不靠手工逐条录入。两个方向：**导入**（把已有的收藏清单搬进来）、**抓取/下载**（从 provider 取资料与资源） |

## 4. 本轮澄清结论

| 议题 | 结论 |
| --- | --- |
| 使用者与形态 | **未定**。当前阶段目标是"先把数据本身理顺"，界面形态（命令行 / 网页 / 桌面）后置 |
| 第 3 条约束的作用范围 | 约束的是**"库"**，不约束**"工具"**：库里不存音频，但下载类工具可以把音频落到**本地磁盘**（见 §9 合规边界） |
| "从 provider 下载"的对象 | **元数据 + 音频**。音频下载到本地磁盘即可，但不进收藏馆的库 |
| 平台范围 | 国内平台（网易云音乐 / QQ 音乐 / 酷狗 等）、国外平台（Spotify / Apple Music / MusicBrainz / Discogs 等）、视频站（YouTube / Bilibili） |
| 联网底线 | **资料查询完全离线**；唯一需要联网的场景是"从 provider 抓取与下载" |
| 关系范围 | 四类全要，见 §5 |
| 听歌方式 | 不做内置播放器；以**导出歌单交给别的软件**为主 |

## 5. 关系范围（要记什么）

1. **基础关系**（用户举例）：翻唱、属于某专辑、由某歌手演唱。
2. **创作侧**：作曲、作词、编曲、厂牌。
3. **版本与派生**：同一作品的不同录音版本（录音室 / 现场 / 重制 / remix）、采样关系。
4. **个人数据**：歌单、评分、收听记录、心情标签。

## 6. 功能需求清单

> 只描述"要能做到什么"，不含实现方式。

- **R1 音乐档案**：录入、修改、删除一首音乐的档案；档案至少包含名称、流派、风格，以及能标识它的其他信息（年代、语种、时长、版本类型等，字段待定）。
- **R2 平台身份**：为一首音乐登记多个平台的 id 与链接；能通过链接/平台 id 反查是哪一首音乐。
- **R3 关系维护**：建立与解除 §5 中各类关系；能查询一首音乐的全部关系。
- **R4 关系遍历**：从任意一个对象（音乐 / 作品 / 歌手 / 专辑 / 厂牌）出发，按关系向外扩展查看，例如"这首歌被谁翻唱过""这个歌手参与过哪些作品"。
- **R5 收藏与个人数据**：维护歌单、评分、收听记录、心情标签等个人数据，并与音乐档案关联。
- **R6 导入**：把已有的收藏清单（歌单文件、导出文件、纯文本列表等，格式待定）批量导入，且可重复导入而不产生重复数据。
- **R7 抓取与下载**：依据平台链接或平台 id，从 provider 获取资料（元数据）与资源（音频），并把资料写入本地库、把音频落到本地磁盘。
- **R8 离线检索与浏览**：在**完全离线**的前提下按名称/流派/风格/歌手/平台等条件检索，并浏览关系网络。
- **R9 导出**：把结果导出为歌单文件，交给其他音乐软件使用。
- **R10 来源可追溯**：每条数据能说明它是手工录入、批量导入还是从某个 provider 抓取的。

## 7. 约束与非功能需求

- **离线优先（查询侧）**：库一旦建成，浏览与检索不得依赖网络；网络只出现在"入库前的获取"与"下载音频"环节。
- **合规**：见 §9。库内不存在任何音频字节。
- **不重复**：重复导入、重复抓取不得产生重复记录；同一首音乐的多个平台身份应归并到同一条记录。
- **可扩展**：新增平台、新增关系类型不应推翻已有数据。
- **诚实**：查不到就说查不到，不用猜测的数据填充字段。

## 8. 非目标（明确不做）

- 不做音乐播放器、不做解码/转码。
- 不在库中存储、复制、分发任何音频内容。
- 不做版权内容的再分发、不提供绕过平台授权的手段。
- 当前阶段不做界面形态的决策（先把数据理顺）。

## 9. 合规与风险（必须记录）

- **下载能力 ≠ 授权**：工具提供"从 provider 下载音频"，不等于用户获得了该音频的使用授权。下载行为及其后果由使用者对目标平台的条款与当地法律自行负责。
- **库内零音频字节**：这是硬约束，也是本项目的合规立足点 —— 收藏馆只保存"知识"与"指针"。
- **音频落在库外**：下载下来的音频属于使用者本机文件，收藏馆只是知道"它在哪"，不接管它的生命周期。
- **待判定的灰色项**：封面图、歌词是否也算"需要规避的复制内容" —— 未决（见 §10）。
- **平台接口风险**：多数平台没有公开稳定的接口，可能要求登录态、可能随时变动 —— 未决。

## 10. 未决问题（下一轮要回答）

1. 数据主要从哪来？手工录入 / 导入清单 / 抓取，三者优先级如何？
2. "同一首音乐"如何判定并跨平台合并？依据编号（如 ISRC）、标题+歌手，还是人工确认？
3. 封面图、歌词算不算要保存的"内容"？能否落到本地？
4. 个人数据（评分、收听记录、心情标签）从哪来 —— 手动填，还是从平台同步？离线前提下如何记录收听？
5. 歌单导出成什么格式、交给哪些软件？
6. 规模量级：几百首 / 几万首 / 几十万首？（会影响后续选型）
7. 是否需要多人共享或多设备同步？
8. 界面形态最终选什么？
9. "导入列表"具体指哪些格式？是否包括用户本地已下载的音频文件目录（只读元信息、不复制文件）？
