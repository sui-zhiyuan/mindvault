LSH 的关键一步

为什么 8 个 band 就能省掉全量两两比较

只在「至少有一段完全相同」的文档之间比较；相似度越高越容易撞中，8 段并列是为了把「只撞一两段」的小概率也接住。

band 1｜sig[8:16]

band 2｜sig[16:24]

band 3｜sig[24:32]

band 4｜sig[32:40]

band 6｜sig[48:56]

band 7｜sig[56:64]
hash → (doc_id, 7, h₇)

Python 循环不是 UDF

循环次数只取决于配置的 bands，与数据行数无关——它只展开固定的 lazy plan 结构； slice 与 hash 都是原生表达式。

撞中概率（这就是实际阈值）

P(s) = 1 − (1 − s⁸)⁸
s = 0.9　→　95%
s = 0.8　→　61%
s = 0.5　→　3%

fixture 注入的近似重复正是 s ≈ 0.9， 所以模糊合并会被稳定触发；精确重复（s = 1）100% 相撞。

代价

  • 数据膨胀 8 倍，多两次全局 shuffle
  • band 越多：召回越高、误报越多
  • num_hashes 必须能被 bands 整除
结论
参数（64 哈希 / 8 band）本身就是相似度阈值：≈0.9 相似度的文档有 95% 概率被判为重复，0.5 的只有 3%。

业务含义

它到底在解决什么问题、留下什么产物

业务场景：预训练语料的近似去重

  • 精确去重只能删「逐字相同」的文档；web 语料更常见的是转载、模板微调、行尾差异
  • 重复会让模型记忆并复述训练样本，损害泛化，也让评测被污染
  • 白烧 token 预算，且不产生任何新增信息

保留策略

  • 每个分量取字典序最小的 doc_id，fixture 里约等于最靠前那篇
  • 同一规则在 band_rep / component_rep / 保留判断三处复用
  • 想改成按质量分保留，只需替换这几处聚合表达式

产物与验收

  • 写出 4 列 deduped parquet，并回读计数校验完整性
  • 指标含 input_rows / output_rows / readback_rows 与零 UDF 不变量
  • 零 UDF 是硬断言：物理计划出现 UDF 标记直接 AssertionError

它无法自证「去重生效」

每篇文档至少属于一个 band，孤立文档也会被保留，所以输出行数恒等于分量数、永远非空。 仓库对同类任务的 golden 合同是 has_kept_and_dropped（必须既有保留又有剔除），本 pipeline 自身没有这个保护。

结论
业务上它回答「哪些文档近似重复」，但不回答「删了多少」——别把「跑通」当成「去重有效」。

背景读数（100 行输入 · 单机 3-NUMA 模拟 Ray 集群）

产线实现特征Rust CPU 占比
Pipeline A精确去重，一次 groupby + join2.65%
Pipeline B8× 膨胀 + 两次 groupby + join18.95%
Pipeline C模型评测，多表 join + coverage1.84%
原始文本产线大量 Python UDF0.91%

Rust 占比是 exclusive active CPU sample share，不是墙钟占比。

为什么不做并行扩展

  • sweep 实验的结构性结论：minhash 去重 α ≈ 1.0，N* = 1，切分区净亏损
  • 瓶颈是全局 shuffle / barrier，堆核救不了
  • 最初扫 ray_num_cpus 曲线全平——输入只有一个分区，集群再大也只有一个 task 在跑

两种设定服务两个目的

  • 测集群调度路径 → 设 into_partitions=16
  • 测算法结构效率 → N=1（本 task 未设该参数，默认单分区）
结论
B 的价值不在绝对性能，而在把 Rust 计算窗口放大到可被观测——它是三条约 20% 与 2% 的对照实验里的放大器。

边界与风险

它还不是生产版：4 个必须知道的缺口

缺口具体表现后果 / 修法
不是连通分量 只做单轮 min 传播：没有显式边表、没有 Large-star / Small-star 迭代、没有收敛判据 A–B、B–C 相似但 A–C 不同桶时会漏合并；需按官方示例补迭代与全局最小标签传播
无算法正确性校验 只断言「零 UDF」+ 回读行数一致；官方实现会与 igraph 连通分量结果比对 能保证跑通，不能保证合并对了
哈希函数会降级 _hash64() 依次尝试 xxhash3_64 → 无 seed 版本 → 纯 hash() 任务声明承诺 xxhash3_64，降级后实际实现可能不同，是跨环境复现的隐性变量
同仓库两套 MinHash DJ 风格版是纯 Python 单 band（num_perm=16）；本 pipeline 是 8 band 原生实现 normalization / ngram / seed / 哈希变体全不同，跨系统对比必须逐项对齐

另外：runner/input_loader.py 与 paths.py 不在仓库历史里（真实运行依赖测试服部署环境）， 该 checkout 开箱不可执行；Daft 版本 pin 为 0.7.2。

结论
前两个缺口是算法级的（合并正确性），后两个是可复现性的——启用前都必须先补。

后续演进与小结

两个 opt-in 优化分支 · 三句话结论

one-pass-bands

VOLC_PIPELINE_B_ONE_PASS_BANDS=1

8 次 select + union_all 换成一次 explode。 原版每个 band 一条分支各自消费整份计划，MinHash 可能被重复计算；改完后 MinHash 只出现一次。

materialize-minhash

VOLC_PIPELINE_B_MATERIALIZE_MINHASH=1

展开前插一次 collect()，避免每个分支重算投影。 代价是切断流水线、签名进 driver 内存，只适合小样本档。

两者都用环境变量 opt-in，baseline 计划仍可复现——延续仓库「性能建议是 opt-in、不是不变式」的约定。

一句话结论

  • 输入：两列 parquet/lance（doc_id, text），来自 web 正文抽取后的语料
  • 处理：规范化 → 64 维 MinHash → 8 band 展开 → 桶代表 → 分量代表 → 选代表写出（两次 shuffle，零 UDF）
  • 输出：4 列 deduped parquet，每分量保留 1 行，回读校验
  • 场景：语料近似去重；工程上用 8× 膨胀放大 Rust 计算窗口

下一步可以做

  • 补迭代式连通分量 + 全局最小标签传播，与官方实现对等
  • 输出删除清单与 dedup 计数，让「生效」可观测
  • 锁定哈希实现或把实际实现写进 metrics
  • 对齐 normalization / ngram / seed 后再做跨系统对比
结论
