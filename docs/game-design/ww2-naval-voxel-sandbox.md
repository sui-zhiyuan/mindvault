# 二战风格体素海战沙盒：技术分析与设计

> 更新：2026-09-18

## 简介

本文分析一款 **3D 体素海战游戏** 的技术构成、未被同类产品解决的技术问题与可行性，并给出关键设计的取舍结论。
游戏设定为"二战技术水平的海战环境"，但**不使用任何真实舰船、真实战斗故事与真实型号**，只模拟当时的战斗环境与决策困境。

设计中有三条刻意做出的取舍，它们决定了整套技术方案的形状：

1. **弹道不做真实弹道学**：直射武器按"激光/瞬中"处理，曲射武器用抛物线 + 飞行时间延迟。核心玩法不是弹道计算，而是 **搜索 → 接触 → 摧毁** 三段链路中每一步都可能出错、且指挥官没有全局信息。
2. **玩家与内置 AI 共用同一套底层接口**（参照 Screeps 范式）：内置一份"星际争霸水平"的 AI，玩家可在其上覆盖与扩展。
3. **战略目标点与后勤资源点在地理上强制分离**：收缩防守有巨大战术优势，但会失去战略目标——**龟缩必输，但不会"晚一秒即输"**。

Prerequisites: 需要了解体素渲染、刚体物理、行为树/脚本 AI 与 RTS 信息模型的基本概念。
Related: 浮力模型的完整推演见本文 [附 A](#附-a浮力与进水模型)。

## 核心内容

### 1. 题材与尺度：为什么"不还原二战"反而是技术红利

不使用真实舰船带来两件事：一是规避版权与品牌识别风险（不使用真实舰名、舷号、徽记，避免复制可识别的舰桥/炮塔轮廓）；二是**美术与数值可以完全服务于玩法**。但更重要的是第三条，它直接决定技术路线：

> 既然不还原二战，就不必承担真实弹道学、真实火控、真实损管的计算与调试成本。
> 真正要保真的是 **"决策者在信息不全时的困境"**，而不是炮弹的空气阻力系数。

由此得到技术规模的定位：

| 维度 | 选择 | 理由 |
|---|---|---|
| 交战距离 | 视觉到数十公里（视武器等级） | 覆盖"目视发现"到"雷达/侦察机引导"两种玩法 |
| 仿真单元 | 体素（细，0.25–0.5m）与仿真大格（粗，1–2m）**分层** | 性能天花板由此决定，见 [附 A](#附-a浮力与进水模型) |
| 单位规模 | 单场 50–300 个单位（舰 + 机群） | 受 AI 指令预算约束，见 §3.4 |
| 时间尺度 | 可暂停、可 1×–8× 加速，帧率无关 | 指挥官视角需要"想清楚再走" |

### 2. 分层架构总览

```
┌──────────────────────────────────────────────────────────────┐
│ L4 玩家界面 / 观察者                                            │
│   下命令（选中单位 → 移动/攻击/侦察）、看信念图、看回报            │
├──────────────────────────────────────────────────────────────┤
│ L3 指挥层（玩家剧本 / 内置 AI 的战略战术层 / 内置舰队模板）        │
│   产出：意图 Intent（对象、区域、时限、ROE、优先级）              │
├──────────────────────────────────────────────────────────────┤
│ L2 单位控制层（玩家可覆盖的 AI）                                 │
│   输入：该单位的信念图 + 收到的意图；输出：动作 Action             │
├──────────────────────────────────────────────────────────────┤
│ L1 统一内核接口（本文的"统一底层接口"）                          │
│   query 只暴露"该实体已知"的信息；command 一律走消息总线           │
├──────────────────────────────────────────────────────────────┤
│ L0 仿真内核（体素、浮力、探测、通信、损伤、弹道简化模型）           │
│   确定性、可 headless 运行、可存档、可回放                        │
└──────────────────────────────────────────────────────────────┘
```

关键原则：**玩家、内置 AI、玩家编写的 AI，三者都是 L3/L2 的普通客户端，接口完全一致、无特权。** 内置 AI 不允许读取真值，玩家 AI 也不允许——这既是公平性，也是"不可能全知"这一核心设计的技术保证（详见 §3.3）。

### 3. 统一底层接口（参照 Screeps）

#### 3.1 为什么必须"统一"

如果给玩家 AI 单独开一套接口，会出现三个必然恶果：内置 AI 与玩家 AI 行为不可比（无法做平衡）、LLM 辅助开发无法复用同一套调试工具、以及信息约束会被人为绕过（内置 AI 偷看真值）。

因此采用 Screeps 的核心范式：**所有 actor 每 tick 接收一个只读的世界视图，返回一组动作**，由内核统一执行与配额。

```
interface Actor {
  tick(view: ReadOnlyBeliefView): Action[]   // 纯函数、确定性
}
```

三种 actor 实现同一个接口：

| Actor | 世界视图来源 | 是否可被玩家覆盖 |
|---|---|---|
| 单位控制器（L2） | 该单位"当前已知"的信念图 | ✅ 可整体替换或局部扩展 |
| 内置战术/战略 AI（L3） | 该指挥部已知的信念图 | ✅ 可继承与覆盖单条规则 |
| 玩家手动命令 | 玩家界面截图（人眼看到的信念图） | —（等价于直接注入意图） |

#### 3.2 命令即消息：手动指挥与 AI 指挥的统一

这是架构上最重要的一条：**玩家的手动命令不是直接改状态，而是投递一条"意图消息"**，与 AI 下达的意图进入同一条总线，经过同样的通信延迟与丢失模型。

- 好处 1：手动指挥与自动指挥**天然可混用**，玩家可以只对 1 艘船手动下令，其余交给 AI。
- 好处 2：**通信受限设计不会被手动操作绕过**——玩家下令也会受延迟与截听影响。
- 好处 3：LLM 辅助开发时，测试只需构造消息序列即可复现任意场景，无需模拟 UI 操作。

#### 3.3 视图即认知：为什么"不可能全知"必须做在线里

`view` 只暴露该实体**当前已知**的信息，而不是仿真真值。每一条观测都携带：

```
Observation {
  subjectRef     // 观测到的目标（可能是猜测的身份）
  position       // 带误差的估计位置
  positionError  // 误差半径（决定命中散布，见 §4.3）
  confidence     // 置信度 0..1（决定是否值得开火）
  observedAtTick // 观测时刻（决定信息是否过期）
  sourceTrail    // 来源链：目视 / 雷达 / 水机 / 友军转发
  identity       // 未识别 / 疑似驱逐舰 / 已识别（分级，见 §4.2）
}
```

由此产生一个非常干净的推论：**AI 的"犯错"不需要专门编写，它是信息约束的自动结果。** 一个只有过期情报的 AI 会扑空、会打错目标、会把商船当军舰——这不是 bug，是设计。

#### 3.4 指令预算与执行顺序

| 机制 | 设定 | 目的 |
|---|---|---|
| 每 tick 指令预算 | 每个 actor 有配额，超限则冻结该 actor 本 tick 剩余决策 | 防止玩家/LLM 写出的规则把帧率打死 |
| 执行顺序 | 战略层 → 战术层 → 单位层，高层先写意图，低层不得覆盖 | 保证"意图优先于动作"，避免下级规则劫持舰队 |
| 预算分级 | 空闲单位预算低、交战单位预算高 | 把 CPU 花在正在决策的地方 |
| 溢出策略 | 超限 actor 记录告警并落盘，可被 harness 读到 | 让"性能问题"变成可验证的失败，而不是玄学卡顿 |

### 4. 弹道简化与"搜索 → 接触 → 摧毁"三段链路

#### 4.1 武器类别（刻意简化）

| 类别 | 模型 | 计算成本 | 玩法作用 |
|---|---|---|---|
| 直射武器（主炮/副炮/防空） | **瞬中（hitscan）**，仅按距离给出可视化飞行线 | 极低 | 交战即结算，决策压力落在"要不要打、打谁" |
| 曲射武器（岸炮、火箭、航空炸弹） | 抛物线解析解 + 飞行时间延迟，落点由 §4.3 的误差决定 | 低 | 提供"提前量"与"落点预判"的玩法 |
| 近防/弹幕 | **概率场批量结算**（一段时间窗合并为期望命中数） | 低 | 支撑高密度防空而不产生万级弹丸实体 |
| 鱼雷/水雷 | 直线/漂移 + 引信判定，属"区域拒止" | 低 | 用于封锁航道与后勤线 |

> 说明：直射武器用"瞬中"处理与二战技术水平存在表观冲突，但这是**刻意的技术取舍**——背景设定可以通过"观瞄设备/火控水平"自圆其说，而计算成本与决策清晰度的收益远大于弹道保真。故事背景层不是本设计的技术约束。

#### 4.2 三段链路：每一段都可能失败

```
搜索 Search ──▶ 接触 Contact ──▶ 摧毁 Destroy
  │                │                  │
  │ 没找到          │ 误判/低估          │ 打空/伤害不足
  │ (漏检)          │ (身份、数量)        │ (情报过期)
  ▼                ▼                  ▼
 继续搜索        错误决策            重新搜索
```

| 阶段 | 判定门 | 失败模式（设计上必须存在） |
|---|---|---|
| 搜索 | `P(发现) = f(距离, 目标信号特征, 海况/天气, 己方传感器等级, 电子压制)` | 漏检（目标就在附近但没发现）；虚警（假回波、诱饵、误报为友军） |
| 接触 | 随时间累积观测提升身份等级：`未知 → 疑似类别 → 已识别` | 误判类别（把小船当主力）、低估数量（编队只看到一半） |
| 摧毁 | 命中概率取决于**己方对目标位置的误差**与武器精度，而非目标真实位置 | 打空（弹药浪费，暴露位置）、过度杀伤浪费火力、错打中立目标 |

**这是本设计的核心机制**：三段链路串起来后，"侦察"从辅助玩法变成主要玩法，因为**没有好情报就没有有效火力**。

#### 4.3 误差传播：把"信息质量"直接接到"命中率"上

```
命中概率 ≈ f(武器精度, 距离) × g(positionError)
```

- `positionError` 大 → 散布大 → 命中率低、弹药消耗高。
- 于是"多派一架侦察机"有了**可直接量化的收益**，而不是靠数值恐惧驱动。
- 情报过期同样如此：用 `observedAtTick` 结合目标可能速度推算**不确定性圆在增长**，过期情报的圆会大到无法有效射击。

这套设计的技术成本极低（几个概率公式），但产生的决策深度极高，是本项目性价比最高的部分。

#### 4.4 通信与反情报（保留原有设计）

- 消息带 `cryptoLevel` 与 `power`；截听与破译按统计概率处理，**不实现真实密码学**：
  `P(截听) = f(距离, 功率, 敌方监听, 频段占用)`，`P(破译)` 随时间累积上升（天然产生"情报有时效"）。
- 侦察机必须回到无线电联络范围才能报信，否则信息"滞留在飞机上"。
- 大功率发报可压制信道，同时**暴露自己**（避免无脑干扰）。
- 玩家看到的是**己方信息融合结果**：过期图标、矛盾报告、"我知道但我方 AI 不知道"。

### 5. 后勤切断：用"射程"与"发现难度"双重限制

#### 5.1 核心机制：远距离打击受后勤半径约束

设定：**所有打击手段的有效射程，都受己方最近可用后勤节点的限制**（弹药、燃油、维修、航空消耗品）。由此：

- 后方资源点天然位于敌方打击半径之外 → **小分队无法直接切断对方后勤**。
- 要切断对方后勤，必须**把成建制的舰队推进到敌方纵深** → 必然携带长补给线、必然长时间暴露。
- 攻方的长补给线反过来成为守方（处于内线）的目标。

#### 5.2 为何"小分队偷袭后勤"在本设计中必然失败

三个机制叠加，使小船队的期望收益为负：

1. **打击半径**：后勤点不在小分队可达范围内，除非带着补给船一起来——那就不是小分队了。
2. **发现难度对称**：正因为缺少全局信息，**对方也找不到你的后勤**；所以偷袭者常常是先迷路、先被对方侦察网发现。
3. **暴露惩罚**：深入敌后意味着长时间处于对方搜索网覆盖内，被发现的概率随时间上升；而偷袭者缺乏防空/反潜掩护，一旦暴露就难以脱离。

结论：后勤切断是**战役级行动**（需要舰队掩护与自身补给线），不是骚扰式小动作。这与"指挥官视角"的定位一致：**要做的是战役决心，不是微操偷袭。**

#### 5.3 资源前运的风险与消耗（设计参数）

| 参数 | 作用 | 建议趋势 |
|---|---|---|
| 前运损耗率 | 每段补给航线按风险系数扣除 | 距离越远损耗越高（非线性） |
| 航线暴露度 | 被对方搜索网覆盖的时间比例 | 与离己方控制区距离正相关 |
| 装卸/会合耗时 | 海上补给窗口，期间编队机动受限 | 使补给成为战术脆弱窗口 |
| 补给节点冗余 | 可被摧毁的前沿仓库 | 前沿仓库被打掉即"能力衰减"，非即刻失败 |
| 补给线可重建 | 重建时间与成本 | 保证被切断是"劣势"而不是"败局" |

### 6. 战略目标与后勤资源点必须分离

**反例（魔兽争霸 / 星际争霸）**：资源点即目标点，扩张即得分，导致"抢点"成为唯一最优解，防守没有结构性优势。
**本设计的分离**：

| 类型 | 位置 | 价值 | 与胜负的关系 |
|---|---|---|---|
| 战略目标 | 远离双方本土（岛屿机场、海峡、海域） | 只有它能推进胜利 | 必须**前出占领并持续保持** |
| 后勤资源点 | 靠近各自本土 / 沿安全航线 | 只提供持续作战能力 | 与经济挂钩，不直接得分 |

由此产生**结构性的战略张力**：

- **收缩防守**：补给线短、兵力集中、不易被发现 → **战术上极强**。
- **但**：战略目标在远方，龟缩就等于放弃得分 → 若对方持续推进，失败仍然是**必然且可预见的**。
- **前出**：能得分，但补给线长、暴露时间长、被发现概率高 → **有代价的进取**。

这正好实现两条要求：**收缩防守有巨大战术优势（不会被一秒钟打死），但无法达成战略目标（龟缩必输）。**

#### 6.1 胜负模型（避免"晚开一秒即输"）

- **胜利条件**：战略目标的**控制度累积**（占领 + 持续保持时间），或时限结算时的控制度对比；不用"摧毁某关键设施即胜"。
- **失败条件**：控制度被反超 / 时限结算落后 / 己方战略目标全部失守且无力反攻。
- **铁律**：
  1. 不允许任何"单点即时失败"条件；
  2. 一切失败必须有**数十秒以上的预警与可干预窗口**；
  3. 软失败（失去侦察、失去制空、被迫撤退）优于硬失败（船没了 = 输了）；
  4. 内置 AI 默认模板必须**开箱可用**，玩家离开键盘不会立刻崩盘——玩家的自定义 AI 是**优化**，不是**生存前提**；
  5. 败方保留后方安全区与可重建产能。

#### 6.2 PVE 的难度设计原则

不给 AI 开全图、不给 AI 加数值。**给 AI 同等的信息约束**——它也会误判、也会被压制、也会扑空。这既利用了 §3–§4 的全部机制，也显著降低了实现难度（不需要为"聪明的 AI"写特殊逻辑）。

### 7. 关键决策：让 LLM 编码代理参与实现（问题 A / C / H 的统一解）

前文识别的三个最难问题——**A：局部且过期的知识与协同**、**C：规则 AI 语言的可用性**、**H：信息匮乏下的可玩性**——本质都是"设计空间太大、迭代太慢"的问题。统一解法不是提高玩家手写 AI 的能力，而是：**玩家/设计师给出需求，由 LLM 编码代理（DeepSeek / Claude Code）实现，而 harness 能访问、验证并理解实现结果。**

#### 7.1 这个方案成立的前提（必须一开始就设计好）

| 前提 | 具体要求 | 不满足的后果 |
|---|---|---|
| 确定性 | 相同种子 + 相同输入 → 逐 tick 相同输出 | LLM 无法复现问题，迭代变成玄学 |
| 可无头运行 | headless 模式，无渲染依赖 | 无法批量自动测试 |
| 可机读的状态导出 | 结构化 JSON/JSONL，schema 稳定且有版本号 | LLM 只能"看截图猜"，无法定位 |
| 可复现回放 | 可从指定 tick 快照重放 | 无法从失败点改代码重试 |
| 稳定 ABI | actor 接口、动作集合、视图字段有语义版本 | LLM 每次改动都要重学接口 |
| 可断言的场景 | 场景带机器可读的期望结论 | "AI 变好了没有"无法判定 |

#### 7.2 调试与验证接口（Debug & Verification Interface）

这套接口的**用户不是玩家，而是 harness 里的 LLM**。因此它必须满足"机器可读、可对比、可断言、变更可检测"。


**（6）闭环工作流**

1. 需求（人类用自然语言写）→
2. LLM 读 `contracts/` + `reports/` 现状 →
3. LLM 改 `content/ai/*` 或内核 →
4. 跑 `mvsim run` + 断言 → 看 `diff` 与 `regression` →
5. 收敛后提交，CI 跑**基准场景集**防回归。

> 注意：这条工作流要求**内核与 AI 分层**。内核改动走引擎回归；AI 与模板改动只走内容回归（秒级）。若两者混在一个仓库里改，LLM 每次都要重编译、重跑长测试，迭代速度会崩塌。

### 8. 内容分发：模板与 AI 代码独立管理（Git / GitHub）

#### 8.1 三类内容必须物理分离，且可独立版本化

| 内容 | 位置 | 版本策略 | 谁维护 |
|---|---|---|---|
| 引擎内核 | 主仓库 `src/` | 语义版本 | 开发团队 |
| 舰船模板（蓝图 + 分舱 + 子系统 + 默认 AI） | `content/templates/<name>/` | 独立版本 + 内容哈希 | 玩家 / 社区 |
| AI 脚本（分层，可覆盖内置 AI） | `content/ai/<name>/` | 独立版本 | 玩家 / 社区 |
| 场景与地图 | `content/scenarios/` | 独立版本 | 社区 / 官方 |

**模板必须包含"蓝图 + 默认 AI"两件东西**，因为一艘船的可用性同时取决于它的构造与它的行为规则；二者分开发布会导致"下载了船但不会开"。

#### 8.2 模板清单（manifest）

```yaml
# content/templates/blue-ddg/manifest.yaml
id: blue-ddg
version: 2.1.0
engine: ">=0.8.0 <0.10.0"
kind: ship
name: "蓝方通用驱逐舰"
blueprint: hull.vox        # 体素蓝图（压缩）
compartments: compartments.json
systems: systems.yaml      # 动力、武器、传感器、补给接口
ai_default: ../../ai/template-ddg@v2
integrity: sha256:...
license: CC-BY-SA-4.0
source: https://github.com/example/blue-ddg
```

设计要点：
- **引擎版本区间**：内容与内核解耦，内核升级时明确哪些内容需要重测。
- **内容哈希**：多人对局与回放校验一致性（防止"改一格装甲"式作弊）。
- **AI 依赖显式声明**：模板引用它默认的 AI 版本，可被玩家覆盖。

#### 8.3 Git/GitHub 工作流

- **分发格式**：推荐 **git 仓库 + tag**（而非二进制包）。分支/tag 天然承载"版本 + 变更历史 + 讨论（issue/PR）"，并且可被 LLM 编码代理直接 clone、读 diff、做修改。
- **一键订阅**：游戏内支持"从 GitHub repo/tag 安装内容包"，并 pin 到具体 commit（保证回放确定性）。
- **内容 CI（关键）**：任何内容包提交 PR 时，CI 自动跑：
  1. manifest schema 校验；
  2. 蓝图合法性（体积/成本/分舱连续/无浮空块）；
  3. 基准场景冒烟测试（该模板能不能下水、能不能听懂基本意图）；
  4. 性能预算（该模板在 300 单位场景下的 AI 预算占用）；
  5. 平衡指标回归（对基准 AI 的胜率、交换比超出阈值则告警）。
- **评审即平衡调参**：PR 上的讨论 + CI 指标，使社区平衡从"论坛吵架"变成"带数据的代码评审"。

> 这套设计的额外收益：由于内容与 AI 都是**纯文本 + 结构化数据**，LLM 编码代理可以直接参与内容创作（生成模板、改 AI、写场景、修断言），与 §7 的闭环完全一致。

### 9. 未解问题与风险

| 问题 | 为什么难 | 现有产品状态 | 难度 | 影响 |
|---|---|---|---|---|
| **A. 局部且过期的知识 + 自动协同** | 需要统一信念表示、时间戳、融合与冲突消解；多数游戏直接给 AI 开全图 | Nebulous / Command: Modern Operations 在人类指挥层做了，未做到玩家可编程 AI 层 | 高 | 极高 |
| **B. "闭合感"：自动系统必须好到玩家不需要干预** | 玩家写的规则会互相挡路、见敌就冲；规模上去后规则爆炸 | From the Depths 靠复杂度自选；Screeps 靠代码 | 高 | 极高 |
| **C. 规则 AI 的可用性** | 编辑器表达力与确定性的取舍；调试困难 | 无人真正解决（Screeps 门槛极高） | 中高 | 高 |
| **D. 体素破损 × 进水的粒度对齐** | 细体素流体不可算；粗化后视觉与物理不一致 | Stormworks / From the Depths 用舱室法，未与细体素破损精细耦合 | 中 | 高 |
| **E. 跨平台确定性** | 浮点不一致、指令集差异；事后无法补救 | 多数游戏放弃确定性 | 中（有解） | 高 |
| **F. 亚视觉精度与数十公里交战共存** | 大世界坐标精度 vs 亚米级体素 | Sea Power / WoWS 各解决半边 | 中 | 中高 |
| **G. 玩家生成内容（蓝图）的平衡** | 自由建造必然收敛出"最优怪物船" | FtD / NavalArt 均存在 | 中 | 中 |
| **H. 信息匮乏的可玩性（而非折磨）** | 通信延迟 + 过期情报会让玩家觉得在跟系统打架 | **几乎没有产品正面解决** | 中高 | 极高 |
| **I. 弹幕/大量实体 + 持续破损的性能** | 万级弹丸、百级飞机、持续体素破损 | 各游戏靠简化藏拙 | 中 | 中高 |

**§7 的 LLM 闭环主要缓解 A / C / H**（把设计空间探索外包给可快速迭代的编码代理），**§5 / §6 的结构性设计缓解 B 与 H 的玩法侧**（内置模板开箱可用、收缩防守不致命）。**D / E / I 是纯工程问题，须在原型期定死。**

### 10. 必须一开始定死的架构决策

这些决策事后极难 retrofit：

1. **仿真粒度分层**（体素 / 仿真大格 / 舱室）—— 决定性能天花板，见 [附 A](#附-a浮力与进水模型)。
2. **确定性策略**：是否要求 AI 与物理跨平台确定性。若要 → 定点数或统一软浮点，越早越好（否则回放、内容 CI、LLM 闭环全部失效）。
3. **信息模型是"观测 + 时间戳 + 置信度"而非真值** —— 渲染图标、AI、UI、通信必须全走这一条通道，事后改造等于重写。
4. **命令即消息**（玩家与 AI 共用总线）—— 决定通信玩法能否被绕过。
5. **AI 指令预算模型** —— 决定大规模是否卡死；超限必须落盘为可读告警。
6. **内核与内容的分层与版本契约** —— 决定 §7 / §8 的迭代速度。
7. **规则语言版本化** —— 玩家的 AI 与模板会跨版本存在，必须能共存与迁移。

#### 11.1 逐项可行性

| 需求 | 可行性 | 说明 |
|---|---|---|
| 3D、二战氛围但无真实舰船 | 高 | 常规；重点是美术规范与法务边界 |

| 指挥官视角但不秒败 | 高 | 纯设计问题，方案见 §6 |

#### 11.2 建议里程碑（每步可独立验证）

| 里程碑 | 内容 | 验收方式 |
|---|---|---|
| **M0** | 浮力内核：一艘盒状船能单侧进水、倾斜、倾覆、下沉 | headless 数值断言：横倾角随时间单调变化且与解析解误差 < 5% |
| **M1** | 体素建造 + 破损 + 舱室增量重算 | 帧时间预算 + 视觉/物理一致性截图对比 |
| **M2** | 统一接口最小闭环：玩家手动令 + 一架侦察机发报 + 过期情报图标 | 同一场景 seed 下两次运行轨迹逐 tick 一致 |
| **M3** | 调试与验证接口成形：`run/step/replay/diff` + 断言 + 报告 | LLM 能在无人干预下改一条 AI 规则并通过回归 |
| **M4** | 内置 AI 与内容分发：模板 + AI 独立包，CI 跑内容校验 | 从 GitHub 安装一个社区模板并跑通冒烟场景 |
| **M5** | 完整场景：单岛争夺（侦察→拦截→炮战→后勤→结算） | 可玩性评估；此时才有资格判断"好不好玩" |
| **M6** | 规模化与优化：200+ 单位、AI 预算、网络/回放接口 | 帧率与带宽预算达标 |

**工作量判断**：M0–M2 是技术风险演示，1–2 人半年内可完成；**M3 是分水岭**——若 §7 的 LLM 闭环跑不通，应退回"参数化模板 AI"而不是继续做脚本语言；M4 之后是内容生产，那是最容易被低估的 60% 工作量。

#### 11.3 一句话结论

把 **"信息约束"当作核心技术而非附属玩法**，把 **"调试与验证接口"当作一等公民而非测试工具**——这两条同时成立时，A / C / H 三个最难的问题就从"设计难题"变成了"可迭代的工程问题"；而浮力、体素、通信都只是工程实现，不是研究问题。

## 延伸

### 附 A：浮力与进水模型

**核心思路：不模拟"水的流动"，只模拟"每个舱室里有多少水" + "船体静力平衡"。**

#### A.1 表示分层（关键设计决策）

| 层 | 粒度 | 用途 |
|---|---|---|
| 建造/视觉体素 | 0.25–0.5m | 玩家意图、外观、破损表现 |
| 仿真单元（cell） | 1–2m 的粗网格（体素的 2³/4³ 超级块） | 标记 `solid / void / 舱壁 / 设备` |
| 舱室（compartment） | 由超级块连通性洪泛（union-find）得到的水密区 | **进水仿真的最小单元** |

舱室**只在船体被修改或破损时增量重算**，不是每帧。

#### A.2 每个舱室的运行时状态（只有几个浮点数）

```
volume          // 舱室几何体积（预计算）
permeability    // 渗透率：机舱 0.8 / 货舱 0.6 / 空舱 0.95
floodRatio F    // 当前被水占据的体积比例 ∈ [0,1]
centroid        // 舱室形心（局部坐标，预计算）
breachArea      // 破口等效面积（受损后累加）
doorLinks       // 与相邻舱室的连通孔面积
pumpRate        // 排水速率
```

每步按 `F` 插值得到 **水质量 / 水形心 / 仍提供浮力的空腔体积**。

#### A.3 每步更新（O(舱室数)，通常 20–200）

- **进水（孔口流量）**：`dF/dt = Cd · A · √(2g·Δh) / volume`，`Δh = 舷外水线 − 舱内水位`。
  → 破口越大进水越快；**只淹到与舷外水面齐平就停**（物理自限，这正是"舱室法"成立的原因）。
- **舱间串水**：同一公式，`A` 取水密门/破口等效面积 → 未关闭的水密门导致连环进水。
- **排水**：`F -= pumpRate·dt / volume`。
- **横倾来源**：单侧淹水 → 该侧质量增加、浮心偏移 → 力矩。
- **自由液面效应（精度的关键一步）**：部分充液舱室产生重心虚升
  `ΔKG = ρ · i_x / Δ`（`i_x` 为自由液面对纵轴的惯性矩）。
  **`F=0` 或 `F=1` 的舱室不产生此项**，所以只有少数舱室需要算，成本极低。

#### A.4 姿态求解（每步一次，很便宜）

给定各舱室 `F`，解静态平衡（heave / roll / pitch），使重力与浮力的合力、合矩为零：

- **简化版**：小角度稳性理论 `GM = KB + BM − KG`，`BM = I_waterplane / V`，`tanθ = M_heel / (Δ · GM)`。够快。
- **精确版**：牛顿迭代 3–10 次，每次对每个水下舱室求"倾斜水面与盒状舱室的相交体积/形心"（对盒体有解析公式）。
  200 舱室 × 8 次迭代 ≈ 微秒级。

#### A.5 与现成刚体引擎的衔接

- 船的刚体交给 Jolt/PhysX；体素经**贪心合并**成少量凸包/盒体做碰撞（几十~几百个 collider）。
- 每帧施加：`逐舱室浮力（力臂天然产生横倾/纵倾） + 波浪激励 + 附加质量/阻尼 + 舵力`。
- 波浪用 Gerstner/正弦叠加，按船长分段加相位差产生纵摇，不做流体解算。
- **断成两段**：段落重新洪泛为两个舱室组，各自独立浮力。

#### A.6 数值安全

大破口瞬间用大步长积分会数值爆炸：`F_new = min(1, F + dF)`，接近 1 时加阻尼，必要时对进水项做子步。

**先例**：Stormworks 的舱室浮力、From the Depths 的分舱与破口/气泵，都印证了该路线的可实现性与玩法效果。

## Q&A

**Q：为什么不直接用真实弹道学，简化后会不会失去二战味？**
A：本设计的"二战味"不在弹道，而在 **信息不全下的决策**（搜索漏检、身份误判、通信受阻）。真实弹道只会增加计算与调试成本，且对决策深度贡献很小；把预算投到 §4 的误差传播上收益更高。

**Q：既然直射武器瞬中，那"打不中"从哪来？**
A：来自情报误差。命中概率是"己方对目标位置误差"的函数，而非目标真实位置——所以**侦察质量直接决定火力效率**，这是本设计的核心因果链。

**Q：收缩防守有战术优势，会不会导致双方都龟缩、比赛变成僵局？**
A：不会，因为战略目标在远方。龟缩方会持续失去控制度，失败是**可预见但缓慢**的。同时由于补给线短，龟缩方仍能长期抵抗——这正好避免"一秒钟结束"。

**Q：小分队偷袭后勤为什么不能成为主流玩法？**
A：三重限制叠加：打击半径受自方后勤节点约束（够不到）、对方也缺乏全局信息（找不到）、深入敌后暴露时间随距离上升（先被发现）。要切断后勤必须投入战役级兵力与自身补给线，收益与成本才匹配。

**Q：LLM 编码代理真的能替代"设计规则 AI 语言"这件事吗？**
A：它能替代的是**实现与迭代**，不能替代**接口设计**。所以 §7.1 的六个前提（确定性、headless、机读导出、回放、稳定 ABI、可断言场景）必须在原型期就位；否则 LLM 得到的反馈是"看不懂"，闭环立刻失效。
