# AgenticAI 沙箱场景 Kunpeng 亲和性能优化

#### 【商业价值】

自规划。面向 Agentic AI 基础设施开展前瞻性能力布局，优化工具执行关键基础设施。

代码解释器与工具调用需要执行模型生成代码和第三方工具，需通过 MicroVM 独立内核边界提供强隔离；同时，Agent 多会话并发、等待模型生成期间的空闲驻留，要求沙箱具备高密度与低成本暂停、恢复能力。

#### 【交付标准】

技术穿刺。完成关键路径分析、重点候选验证和可复现的双平台性能对比，形成技术可行性及继续投入建议，非产品化交付。

- 分析结论：明确 create、pause、resume 的阶段耗时、主要差距、架构与配置影响及证据边界，给出可优化范围。
- 交付优化代码基线 和 patch，交付到【todo】。
- 交付可复现基准数据：包含环境规格、构建参数、完整测试步骤和命令、基线结果、优化前后 A/B 对比及功能回归结果。

#### 【需求描述】

- 优化对象：TencentCloud/CubeSandbox 在 Kunpeng 950 上的 create、pause、resume 关键路径，聚焦 CubeShim/CubeHypervisor、快照与恢复、CubeCoW 及相关节点管理链路。保持已有优势与功能正确性。
- 性能目标：Kunpen 950 达到 AMD 9654 的 120%”；本需求建议以同一操作的性能比 P＝T9654/T950 定义该口径，T 为相同测试协议下三轮平均时延，挑战值 P≥1.20，即 T950≤T9654/1.20（约为 83.3%）。create、pause、resume 分别判定。
- 指标口径：create 采用请求发出至收到响应头的工具计时，不含响应体读取与解析；pause、resume 按官方脚本同名 avg、p95、per_* 字段分别记录，明确计时范围。

#### 【验收标准】

1. 硬件与系统：测试平台为 Kunpeng 950（aarch64）和 AMD EPYC 9654（x86_64）裸机。
2. 代码与制品：以 https://github.com/TencentCloud/CubeSandbox 的 v0.7.1 为基础版本，两平台固定同一基础提交，记录各运行组件的实际提交、build-id、编译选项与工具链版本。
3. 测试方法：沙箱规格统一为 2 vCPU / 2 GiB，模板内容、构建顺序、缓存状态、复位方式与资源策略按测试规格清单执行。
    create 使用 cube-bench 的 create-only 模式，参数为 -c 100 -n 100 -w 3，热身结果丢弃；
    pause/resume 使用官方 bench_pause_resume_concurrency.py，参数为 -c 10 -n 5，按脚本先执行并丢弃一轮内置热身。
    两类测试均独立执行三轮，每轮执行后需恢复环境遗留沙箱，分别记录各轮结果和三轮均值。
4. 公平性与功能检查：两平台采用相同测试工具版本、调用方式、并发、轮次和沙箱规格，清理残留实例并控制后台负载。ARM 每轮正式测量前冷重启并重建模板，双方记录并保持相同模板构建顺序。
5. 判定方式：按各操作三轮均值计算性能比，分别给出是否达到挑战目标的结论，同时提交优化前后 A/B 数据；create 成功率须为 100%，pause/resume 无操作失败。

#### 【外部依赖】

- 机器与环境：符合测试规格清单的 Kunpeng 950 与 AMD EPYC 9654 服务器、支持KVM 能力、支持 XFS reflink 的数据盘。
- 软件与工具链：匹配版本的 Rust/Go 原生构建环境、官方压测工具与 Python SDK，宿主 OS 使用 openEuler 24.03 LTS-SP3。
- 上游社区：依赖 CubeSandbox 及相关虚拟化组件的版本、修复与兼容性信息，必要时通过 issue/PR 推动修复与原型反馈。

#### 【约束条件】

- MicroVM 的运行状态与快照不可跨 x86_64/aarch64 迁移。
- 基线数据使用 CubeSandbox 中 v0.7.1，必要功能修复采用可追溯补丁单独合入。
- ARM 存在同镜像、同配置模板随构建顺序产生性能漂移的已知问题；按统一顺序构建，不以模板顺序差异宣称优化收益。
- 本 SR 不涉及 PVM 和 虚拟机的的沙箱环境运行时内容。
- 若涉及内核内优化，可在现有版本基础上，以补丁形式合入。
