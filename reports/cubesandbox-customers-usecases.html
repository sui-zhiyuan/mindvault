三类假设核对：安全限制与多租户隔离已有客户实证，Android 模拟尚缺公开案例

假设 → 结论 → 依据
假设结论依据
限制 Harness 执行命令✔ 成立
官方主线		 CubeVS 内核态 eBPF 做沙箱间网络隔离，CubeEgress 按域名 / 路径 / 方法限制出站并注入凭据，Key 对沙箱内代码不可见；trpc-agent-go 案例即"安全代码执行后端"
服务端多租户隔离✔ 成立
有直接案例		 花椒原痛点是"用户 A 可经 Agent 操作到用户 B 的文件"；广晟数科用 owner_id + 租约 + fencing token 做多租户治理，准入上限 200 → 500
模拟 Android 手机⚠ 缺公开案例
技术同源		 官方仅有 Ubuntu 桌面沙箱（noVNC GUI 自动化）集成；AOSP Cuttlefish 虚拟设备本身运行在 VM 中；本 PPT P6 的 Android-Cuttlefish 与 P16 的 Android 沙箱密度为内部数据，宜列为规划
对第 5 页的用法：前两条可直接写成"安全防护 / 多租户隔离"的客户实证； Android 模拟建议标为内部规划，并引用 P6 的 Android-Cuttlefish 与 P16 的 Android 沙箱密度数据。
沙箱能力 → 支撑的场景
内核级隔离
独立 guest 内核 + KVM microVM 支撑：不可信代码执行、多租户物理隔离
网络隔离
CubeVS 基于 eBPF 的内核态转发 支撑：阻断沙箱之间互相访问
出站管控
CubeEgress 出口网关 + 凭证托管 支撑：域名 / 路径 / 方法策略，Key 不进沙箱
状态管理
快照、克隆、暂停与恢复 支撑：会话常驻、技能快照秒级就位
密度与启动
<60ms 启动 · <5MB 开销 · 单机数千实例 支撑：RL rollout 高并发、成本优化
平台能力 已验证场景
结论：客户买的是"不可信代码 + 多租户 + 私有化部署"；Android 场景待补公开案例
